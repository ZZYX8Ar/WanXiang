fix(battle-ui): 卡死真因（倍速+自动 → Delay(0) 全速循环）+ 行动条慢一拍终修

用户（崩溃边缘）："点击自动战斗开倍速就卡死了，什么都点不了只能关编辑器"

一、卡死真因 —— 播放节奏用"秒"驱动，倍速把它压没了
  旧：await UniTask.Delay(TimeSpan.FromSeconds(wait));
      wait = IntervalOf(kind) / _speed —— 倍速(_speed=4) 时小间隔事件（ActionEnd=0.10/4=0.025s）
      甚至四舍五入到 0 ⇒ Delay(≈0) 每帧完成几十次 ⇒ 播放循环全速狂奔，
      一场几千个事件连同 ApplyFrames/ApplyEvent/UI 全部瞬间跑完 ⇒ 编辑器卡死。
  修：**帧驱动** —— 把等待换算成帧数，每次至少等 1 帧（最多 240 帧）：
      int frames = Mathf.Clamp(RoundToInt(w2 * 60f), 1, 240);
      for (...) await UniTask.Yield(PlayerLoopTiming.Update, ct);
  ⇒ 永远不会全速；倍速只是"帧间隔变小"，节奏手感不变。

二、行动条慢一拍 —— "当前行动者"在两种状态下语义不同
  等玩家下令时，_play.Current 还停留在**上一单位的收尾事件（ActionEnd）**上，
  按它的 actorId 找 cur ⇒ 高亮永远指上一个（用户反复实测）。
  修：**两种状态分开**：
    if (AwaitingCommand) cur = PendingUnit;      // 等令：待令单位就是"该行动的"
    else { 按 Current.ActorId 找 cur; }           // 演出中：跟随画面
  （上一轮把两种语义合并成一个优先级判断，就是反复修不掉的原因。）

三、连携技设计说明（答复用户疑问）
  连携是**主动发动**（v2.1 把"连携技发动"列为四大决策点之一）：
  双方各扣 2 灵力、每场每条一次 ⇒ "什么时候放连携"本身就是策略决策。
  若要改成被动触发（同场自动放），需重设计资源逻辑 —— 待用户定夺。
